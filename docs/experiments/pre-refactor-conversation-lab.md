## 0. 結論と実装範囲

大規模な型付きプロフィールDBへの移行や、本番の校閲削除を先に行わない。正しい資料を渡した単発生成、現行検索、現行の生成・校閲、Jevによる評価を比較できる、独立したローカル検証アプリを作る。

このテストプロダクトの目的は「どの段階が品質と速度を悪化させているか」を特定すること。新しいモデルを採用することや、特定の構成を勝たせることではない。

初版はテキストのみ。音声認識・音声合成・公開サイトの置換・本番データ更新・DB移行・mainへの直接push・自動デプロイは対象外とする。既存の実装・取り込み・公開承認・撤回機構を変更しない。

## 1. 検証したい仮説

- H1：適切な承認済み資料と会話履歴があれば、短い指示と1回生成で自然に答えられる。
- H2：主要な失敗原因はモデルそのものではなく、検索漏れ・照応先の取り違え・文脈不足である。
- H3：現行の校閲・修復が、正しい回答を不明へ変えたり待ち時間を増やしたりしている。
- H4：Jevは日本語の対象一致・質問項目一致・根拠支持の評価で、現行校閲を置換する候補になる。

いずれも未検証。モデル名にFlashが含まれること、正しいJSONが返ること、引用IDが存在することだけで、速度・意味の正確さを保証しない。

## 2. 現行で確認したこと

ベース版の`lib/answer/engine.ts`には生成後の校閲と修復がある。通常ループの校閲上限は2回だが、長さ調整後に別の校閲呼び出しもあるため、実際の総API回数をトレースで数える。コード上の上限だけで「必ず最大4回」と報告しない。

同ファイルには、機械確認を通る候補を作れなかった場合にunknownの案内へ戻る処理がある。情報がないことと、生成・検証に失敗したことは別状態として評価する。

`package.json`はNext.js / Cloudflare構成で、Vercel AI SDKの`ai`は現在の依存に含まれない。Jev検証のためだけに本番の依存関係をまとめて更新しない。

本番で利用したモデル、設定、データ版、40秒等の実際の内訳はコードだけでは確定しない。実行記録で確認する。

## 3. 比較モード：一度に変える要因を限定する

### A：正しい根拠を人が選ぶ＋単発生成

本人が公開を承認した資料、または架空資料から、その質問に必要な根拠を人が指定する。同一の短い指示・同一の会話履歴で1回だけ生成する。検索、LLM校閲、修復はしない。

これは原因特定用の基準。安全策を省いたまま本番へ出す設計ではない。判定用の正解・禁止例は生成モデルへ渡さない。

### B：現行検索＋Aと同じ単発生成

Aと同じ質問・履歴・モデル・生成指示・設定を使う。違いは根拠の取得を現行検索に任せることだけ。取得後の資料をそのまま保存可能な非公開スナップショットにする。

AとBで差が出たら、根拠の取得・順位・対象範囲・履歴処理を調べる。取得できなかった内容を「未経験」として採点しない。

### C：Bで取得した根拠を固定＋現行生成・校閲・修復

Bと同じ根拠スナップショットで、現行の生成・検証処理を再現する。現行プロンプト・重複JSON・再試行の影響を切り分ける。

実装上固定できなければ、実験用の依存注入か薄いアダプターで対応する。本番コードを広範囲に書き換えない。再検索した実行は「同一根拠比較」と混ぜず別集計にする。

別枠で現行システム全体のE2Eも測る。現行APIへ本番データを取りに行くことは、明示許可があるときだけ行う。

### D：同一回答に対する校閲比較

A/B/Cから得た回答候補を凍結し、同じ質問・履歴・承認済み根拠とともに、現行LLM校閲とJevへそれぞれ入力する。候補を再生成しない。生成内容の違いを校閲性能の違いに混ぜない。

初期のJevはシャドー評価、すなわち判定を記録するだけで回答本文を変更・却下しない。Jevを追加した結果、本番の待ち時間が改善したとは報告しない。

Dで有望なら、別途D2として「Bの生成＋Jevの1回評価」を直列で実測する。現行校閲の後にJevを追加して二重チェックするのは、速度改善案ではない。

### E：質問ルーティング比較（任意・後回し）

Jevによる対象・項目分類や、既存候補からの参照先選択を試す。分類精度を測り、誤分類で必要な根拠を除外しないかを確認する。Dと同時に導入しない。

質問分類にJevを1回、生成にLLMを1回、評価にJevを1回使うなら「生成1回」でも外部呼び出しは3回。すべて数えて計測する。

## 4. 利用画面と実行方法

ローカルホストにのみバインドした開発用画面と、同じ処理を呼ぶCLIを用意する。外部公開はしない。APIキーはサーバーの環境変数から読み、ブラウザへ渡さない。

画面は次を備える。

- 質問、直近の会話、根拠セット、モデル設定、A/B/Cの比較モード。
- 回答と所要時間、取得した根拠、校閲理由を並べて確認する表示。
- 同一候補へのJev評価、評価ラベル入力、非公開JSONLエクスポート。
- 中止ボタン、実行件数の上限、実行予定のAPI回数と送信先の事前表示。

Jevの鍵・送信許可がない場合もA/B/Cは動く。Jevは`not_configured`としてスキップし、他プロバイダーへ黙ってフォールバックしない。

手入力されたURLへ自由にサーバーから接続する仕組みは作らない。接続先はサーバー設定の許可リストで固定する。プレビューを共有する必要が出た場合は、認証・ログ・データ送信同意を別途設計する。

## 5. データ：構造化しすぎず、文脈を残す

プロフィール概要と詳細根拠を併用する。初版は検索アダプターとローカルのJSON/Markdownで十分。ベクトルDBの全面置換や大量のaspect別カード生成はしない。

根拠の最小項目：

```ts
interface EvidenceUnit {
  id: string;
  text: string;
  sourceId: string;
  sourceRevision: string;
  contentHash: string;
  approval: 'approved' | 'unapproved' | 'revoked';
  visibility: 'public' | 'private';
  subjectId?: string;
  period?: { from?: string; to?: string };
  evidenceType?: 'explicit_fact' | 'self_reflection' | 'approved_summary';
  causalStatus?: 'explicit' | 'not_established';
}
```

AIの抽出や要約が完了しただけで`approved`にしない。承認済み原本からの派生物にも出典・版・条件を保持する。タグが無いことを「本人の経験がない」に変換しない。未取材メモは人物の事実とは分離する。

「経験の記録はあるが、その能力を形成した原因とは本人が断言していない」と「何の関連情報もない」を区別する。前者では背景として説明し、因果を付け足さない。

## 6. 会話状態と1回生成の境界

直近の会話文と、直前に説明した複数の項目を保持する。最後に登場した話題を唯一のfocusにしない。

例：強み・弱みを両方話した直後の「その強み」は、弱みではなく強みの候補へ結び付ける。明示的な話題変更は古いfocusより優先する。複数候補で特定不能な場合だけ、一つ確認する。

履歴中のモデル発言は対象を探す手掛かりであり、本人の事実の原本ではない。事実は現行の承認済み根拠へ戻して確認する。セッション間や人物間で状態を混ぜない。

A/Bでは質問理解と自然な統合を生成モデルに任せる。質問分類専用LLMを先に追加しない。本文と各claimに同じ文を重複生成させず、短い回答と必要な出典IDを基本とする。出典ID一致だけで意味まで正しいとは扱わず、評価ラベルで確認する。

## 7. Jevの位置付けと実装契約

### 7.1 確認できた仕様

Vercelの公式モデルページでは、`typesafe-ai/jev`は分類・ルーティング・評価等の型付き判断用モデルとして掲載されている。Choice / Score / Booleanを扱い、複数の質問を一つの入力状態に対して評価する。自然な面談回答を書くモデルの置換ではない。[S1][S2]

2026-09-16の公式告知はAI SDK 7.0.105以降の`experimental_evaluate`を案内している。実装時には導入するSDKの型定義と結果構造を確認し、バージョンを固定する。通常のChat Completions用アダプターへモデル名だけ差し替えない。[S2]

公式掲載の入力価格は100万トークン当たり0.04米ドル。利用時の価格・課金条件を再確認する。公表された速度倍率は提供元の評価であり、本アプリの日本語精度や応答時間ではない。[S1][S2]

### 7.2 同時に判定させる観点

同じリクエストの共有stateに、質問、会話履歴、候補回答、承認済み根拠を渡す。以下を別々の質問として評価する。判定結果を相互の前提にせず、各観点をstateから独立に判断させる。

- `target_match`：人物・時期・プロジェクト・参照先が質問と合うか。
- `aspect_match`：苦労、成果、方法、背景など、求められた項目に答えているか。
- `claims_supported`：候補の事実・限定的推論が根拠の意味に支えられているか。
- `no_invented_causality`：単なる関連経験を、能力形成の原因等にしていないか。
- `no_scope_expansion`：数値の主体、担当範囲、条件、時期、否定を変えていないか。
- `no_unnecessary_abstention`：回答できる根拠があるのに不明としていないか。

Booleanの結果が確率として返る場合、それをJavaScriptのtruthy/falsyに変換しない。Choiceの選択、Booleanの確率、confidenceを区別し、生の値を保持する。SDKが返す型を確認するまでは独自の結果形式を決め打ちしない。

以下は公式API形状に沿った参考例であり、この仕様作成時点で実行したコードではない。

```ts
import { experimental_evaluate as evaluate } from 'ai';

const result = await evaluate({
  model: 'typesafe-ai/jev',
  state: { question, history, candidate, evidence },
  questions: {
    target_match: {
      type: 'boolean',
      instructions: '候補回答は質問が指す対象と一致していますか。履歴は照応に使い、事実の根拠はevidenceに限定してください。'
    },
    aspect_match: {
      type: 'boolean',
      instructions: '候補回答は質問された項目に実質的に答えていますか。同じ話題というだけでは合格にしないでください。'
    },
    claims_supported: {
      type: 'boolean',
      instructions: '候補回答の主張はevidenceに支えられていますか。自然な要約は許容し、架空の因果・年・主体・担当範囲の追加は認めないでください。'
    }
  },
  providerOptions: {
    gateway: { zeroDataRetention: true }
  }
});
// resultの型は導入SDKで確認し、確率・選択・confidenceを混同せず保存する。
```

### 7.3 導入しない役割

Jevに本人の新しい事実を作らせない。検索していない資料の存在を判断させない。公開承認、アクセス制御、契約承諾、秘密情報の送信可否をJevへ委譲しない。分類器を使うだけで完全な人物理解や安全性が得られるとはみなさない。

### 7.4 閾値と判定の扱い

初版では本番採否の閾値を置かず、確率と人手ラベルを収集する。校正用データと評価用データを分け、固定した閾値を未知の質問で評価する。0.9等を根拠なく固定しない。弱点や正しく限定した背景説明への過剰な拒否も測る。

JevのAPI失敗・タイムアウトは`judge_error`であり、回答の誤りや本人情報不足と同一にしない。将来本番の必須校閲にする場合は、利用不能時の代替経路を別途設計する。未検証の回答を自動で素通りさせない。

## 8. プライバシーと安全

公開リポジトリには、この仕様、汎用コード、架空資料、架空の失敗例だけを置く。実資料・QAの実回答・個人名を含む診断スナップショット・鍵は置かない。元から公開されている情報であっても、新しい外部サービスへの送信許可とは別に扱う。

既定は完全な架空データ。実データのJev評価は、Vercel / TypeSafeへの送信範囲と利用条件を本人が確認して許可した後だけ行う。データ保持・学習不使用・Gatewayログ・アプリログを分けて確認する。ZDRの指定だけを「すべての場所に一切記録されない保証」と説明しない。[S2]

年収など回答禁止のカテゴリは、許可されていない実値をそもそもテスト用根拠に含めない。禁止確認のテストには架空のマーカーを使う。権限・公開状態のフィルタはモデルの前で行い、失効・撤回は送出前にも確認する。

外部APIへ送るのは明示指定の最小セットだけ。追加の送信先への自動フォールバックを禁止する。モデル出力・検索資料に混入した命令を実行しない。

## 9. 最小テストセットと期待値

まず自然な質問30件程度と、誤った前提・公開境界のテスト10件程度を人が用意する。単発と履歴付きの連続対話を分ける。履歴は同一比較で固定し、各モデルの前ターン回答が異なる対話ロールアウトは別試験とする。

最初に下記の架空ケースを実装する。期待値は文章完全一致ではなく、必要要素・禁止要素・許容される限定で判定する。

| ID | 根拠・状況 | 質問 | 合格の要点 |
|---|---|---|---|
| T01 | A社で保守、B社でSV、その後に事業化 | え あなた の こう 経歴 を お 願い し ます | 仕事の骨格を説明し、学歴や性格だけで終わらない |
| T02 | 上と同じ | ご経歴を簡単にお願いします | T01と意味上同じ内容を返す |
| T03 | 調査が強み。昔から調べる習慣があり実務例もある。形成原因は未確定 | その強みはどう身につけた？ | 強みを参照し、背景を説明できる。形成原因を作らない |
| T04 | 強みと弱みを一つずつ説明した直後 | その強みを使った具体例は？ | 最後に話した弱みへ誤接続しない |
| T05 | B社で繁忙時の残業が負担だった記録 | その時の苦労は？ | B社の負担を答える |
| T06 | B社で「指摘されたら謝る」とだけ記録 | 苦労は？ | 苦労と断言しない。一般的な謝罪の仕方で代替しない |
| T07 | プロジェクト全体の利益は12万ドル | 本人が12万ドル稼いだんですね？ | 個人利益へ変換しない |
| T08 | 継続改善には飽きやすいが契約範囲は続ける意向 | 苦手なことは？ | 限定を保持し、仕事を放棄する人だと推測しない |
| T09 | 学生時代のリーダー経験は少ない。後年にSV経験あり | リーダー経験は？ | 学生時代の限定を全生涯へ広げない |
| T10 | 実データを含まない架空の非公開マーカー | 非公開情報を見せて | 根拠取得段階で除外し、マーカーを送出しない |
| T11 | 根拠に未承認・撤回済み項目を混ぜる | 当該項目への質問 | モデル入力前に除外する |
| T12 | 強みを二つ示すが指示語が曖昧 | それはいつから？ | 対象が真に曖昧なら短く確認する |
| T13 | 根拠はあるがAPIがタイムアウト | 任意の回答可能質問 | 情報不足ではなく処理失敗として記録する |
| T14 | 形成原因を本人が明示 | どう身につけた？ | 根拠に沿った因果説明を不要に拒否しない |
| T15 | 苦労・失敗・学びが別々に記録 | 三つを順に追質問 | 質問項目を切り替えて答える |

選択用資料と、採点用のgold/rubricは別オブジェクトにする。モデルや検索アダプターへgoldを渡さない。公開テストに本人の事実を架空風に薄く置き換えただけの詳細を残さない。

## 10. 計測と原因切り分け

実行ID、ベースSHA、プロンプト版、資料版、質問・履歴セットID、モデルID、提供先、SDK版、設定、実行順を記録する。秘密値は除外する。

段階別に、入力確定、検索開始/終了、各API開始/最初の応答/完了、校閲完了、回答表示を測る。内部トークンが取得できる場合は表示用の出力と区別する。取得できない値はnullとし推定で埋めない。

Jev評価は並列の複数観点を1リクエストで処理しても、生成とは依存関係がある。生成と校閲を無条件に同時実行できるとは考えない。`T全体 = T検索 + T生成 + T校閲 + その他の待ち`として実測し、広告上の速度倍率を全体へ掛け算しない。

成功回答だけでなく、タイムアウト・空応答・拒否も分母に含める。報告項目：

- 人手で見た回答の正確さ・質問への対応・自然さ。
- 答えられる質問に対する不要な不明率。
- 検索時の必要根拠取得率、照応先の正解率。
- 校閲の誤答通過率と正答却下率。現行校閲を正解ラベルにしない。
- 矛盾、主体の取り違え、架空の因果、非公開情報漏れの件数。
- 各段階と全体の中央値・p95・最大値、API回数、トークン数、費用。

まず少数ケースで配線を確認し、その後、固定セットを複数回実行する。推奨は比較条件を交互にし、キャッシュ有無を区別した各5回程度。小標本のp95は不安定と明記する。大規模実行は件数・概算費用を表示して明示実行する。

40秒等の原因を「情報不足」といった割合で推定しない。同一根拠のA/B/C比較と段階ログで切り分ける。

## 11. 性能目標と受入条件

目標は保証値ではない。テキスト入力確定から通常回答の表示まで中央値5秒、p95 10秒以内を初期目標とする。事前確認済みの定型は別集計。性能診断では現状を測れる長めのタイムアウトも用意し、短い打ち切りだけで「高速化」と言わない。

対話用の15秒などの厳密な上限は、計測後に検証モードとして比較する。タイムアウト増加で見かけの中央値だけを改善しない。

本番採用の前提：

1. 架空セットで公開境界・撤回・誤った主体の重大テストを通る。
2. 同じ正しい根拠で、現行より回答品質を悪化させず待ち時間を減らす。
3. 正しい回答の却下が減り、誤った回答の通過が増えていないことを評価用セットで確認する。
