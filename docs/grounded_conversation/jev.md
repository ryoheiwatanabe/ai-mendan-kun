# JEVを使う本体の回答処理

2026年9月18日にJEVの採用を決定し、既存のテキスト・音声APIへ接続した。本人用の保護されたプレビューで有効にし、公開中サイトの切替とmainへのマージは本人試用後に行う。

## 通常の処理

既存のルーティング・公開根拠検索 → JEV①（生成前の資料選別） → `{text, answerability, evidenceIds}` の候補生成 → 形式・根拠ID・文字数・名前の確認 → JEV②（回答の点検） → 公開状態の再確認 → 表示・読み上げ。

JEVは旧LLM校閲を置き換える。通常はJEV2段階（①と②）と生成1回で、形式や意味の修復が必要なときだけ生成1回とJEV③を追加する。したがって1問あたりの外部呼び出しは、生成が通常1回・最大2回、JEVが通常2回・最大3回。段階の上限は設定の`maxSerialStages`（初期値3）で、上限まで毎回使うわけではない。修復後も点検し、不合格の本文は表示・音声化しない。旧校閲への自動切替や、生成後の追加検索は行わない。

### 生成前の選別（JEV①）

検索で届いた候補資料そのものを、1回のリクエストへまとめた10個までの独立判定で見る。判定の型は用途で使い分ける。

| 型 | 項目 | 返るもの |
| --- | --- | --- |
| Choice | 答えられる範囲（answerable / partial / insufficient / ambiguous） | 選択と分布、confidence |
| Choice | 資料の役割（direct / background / irrelevant / conflict / mixed） | 選択と分布、confidence |
| Choice | 主な根拠（検索候補のIDから選択肢を動的生成） | 選択と分布、confidence。候補集合の外は採用しない |
| Score | 支持の強さ（0〜3の段階） | 段階値（小数）とconfidence |
| Noul | 対象一致・時期一致・直接支持・背景の有用さ・因果の明記・矛盾の危険 | 確率 |

stateは役割ごとの名前付きJSON（`subject` / `question` / `history` / `answer_policy` / `candidate_evidence` / `task`）で渡し、instructionsから名前で参照する。コード側で扱えるもの（件数、日付比較、ID所属、公開状態、文字数、閾値比較、採否の合成）はJEVへ聞かない。

返ってきた答えは、スコア閾値とは別にconfidenceも保存し、閾値未満を低確信として扱う。行き先は設定で選ぶ（そのまま使う／もう1段階だけ聞き直す／控えめな範囲へ落とす／回答を保留する）。確信度は正答率ではない。

選別の結果は生成の入力（`answerScope`）としてだけ渡す。選別の通信失敗・不正な応答では回答を止めず、指示なしで生成へ進み、`scope_error`と`scope_skipped(scope_unavailable)`を残す。最終点検（JEV②）は必ず行うため、選別が失敗しても未検証の本文は表示されない。時間が足りないときは始めずに`scope_skipped(time_insufficient)`を残す。

最終点検（JEV②）のstateにも、選別が決めた回答可能範囲（`answer_scope`）を渡し、同じ範囲に照らして判定する。

### 修復の時間確保

修復の全文再生成は、直前の生成と同じくらいの時間が残っているときだけ始める。残り時間に収まらない場合は始めず、`repair_skipped(time_insufficient)`を記録し、`ANSWER_TIME_SHORT`として「時間内に回答をまとめられませんでした。」を返す。時間切れの案内は、`JEV_UNAVAILABLE`・`ANSWER_REJECTED`と区別する。

Factとチャンクを共に渡し、送信前・JEV直前・最終送出前に公開・承認・所有者・現行版・本文を再確認する。音声の生成・配信中も既存の再確認を維持する。会話履歴は今回のリクエストの直近2往復までで、合計3,600字を超える場合は直近1往復に絞る。履歴を事実の根拠にはしない。定型の挨拶・拒否、対象確認、根拠がない案内、有効な経歴概要キャッシュには生成やJEVを追加しない。

JEVの通信・応答形式の失敗は `JEV_UNAVAILABLE`、点検不合格は `ANSWER_REJECTED`、生成等の失敗は `ANSWER_PROCESSING_FAILED`。本人の情報不足と区別し、入力へ復帰する。中止は生成・JEV・音声へ伝える。JEVが確認した本文を変更せず表示・読み上げる。

## 設定と切り戻し

| 設定 | 値・用途 |
| --- | --- |
| `ANSWER_PIPELINE` | `jev_v1` で有効、`legacy` で旧経路。未指定はlegacy。 |
| `TYPESAFE_API_KEY` | Workers Secret。値を設定ファイルやブラウザへ渡さない。 |
| `JEV_TIMEOUT_MS` | 1回のJEV通信はデフォルト4,000ms。 |
| `ANSWER_TIMEOUT_MS` | 検証済み本文を返すまで。既定60,000ms（上限）。読み上げ待ちは別。 |
| `JEV_THRESHOLDS_JSON` | 下記6軸の閾値を必要な軸だけ上書きするJSON。 |

## 呼び出し先の比較（2026-09-19）

`env.AI.run('typesafe/jev', ...)`（Cloudflare Workers AI）を、公式HTTPと同じstate/questionsで比べられるようにした（`/admin`の「判定の呼び出し先」と`POST /api/admin/jev-probe`、架空の資料のみ・1〜5回）。実測は次のとおり。

| 呼び出し先 | 結果（10判定） | 時間 | トークン |
| --- | --- | --- | --- |
| TypeSafe公式HTTP | 成功3/3 | 211〜499ms | 入力1,481・出力282 |
| Cloudflare Workers AI（typesafe/jev） | 失敗3/3（`Insufficient AI Gateway credits`） | 259〜845msで失敗 | - |

Workers AIはAI Gatewayのクレジットが無いため比較できない。購入の判断は本人に委ね、既定は公式HTTPのままにする。クレジットを追加した場合は同じエンドポイントで再測定できる。

## 候補の絞り込み（任意）

検索候補が多いとき（既定では12件超）に、候補IDごとのScoreで絞ってから選別する段階を選べる。段階数が3のときだけ動作し、使うとその質問では修復ができない。失敗しても全候補で選別・点検を続ける。既定はオフ（段階を修復に残すため）。

生成は既存のOpenCode Go / OpenAI互換Providerを使用する。今回の試用設定は既存の `glm-5.3-flash`、検索は既存のWorkers AI、STT/TTSは既存のGemini。JEV送信先は `https://api.typesafe.ai/v1/systemone` に固定し、リダイレクトしない。送信先は質問前の既存画面にも表示する。

初期閾値は、対象一致0.80、項目一致0.65、根拠支持0.80、因果の非創作0.80、範囲保持0.80、不要な棄権の回避0.60。各軸を独立して判定する。因果や主体の不合格を他の高得点で相殺しない。暫定の採否基準であり、校正された正答確率ではない。

試用版には `PREVIEW_ONLY=true` とWorkers Secretの `PREVIEW_ACCESS_TOKEN` を設定し、Assetsの `run_worker_first=true` を使う。鍵がなければ拒否する。`scripts/protected-preview.mjs` は127.0.0.1だけで待ち受け、サーバー側で鍵を付ける。起動時に `MENDAN_PREVIEW_URL` と `MENDAN_PREVIEW_TOKEN` を安全な取得元からプロセスへ渡す。質問・回答・根拠の本文は保存せず、`MENDAN_PREVIEW_LOG` へ固定のコードと数値だけを残す。

## 失敗したときの確認

回答が失敗しても、どの段階で止まったかを後から確かめられるようにする。残すのは固定のコード・件数・所要時間だけで、質問・回答・根拠の本文は含めない。

- 画面: 失敗した質問の下に、直近8件の段階を `コード(理由) 時間` の並びで表示する。表示は `DEBUG_TRACE` のあるプレビュー版で、回答のヒット率を表示する設定が入っているときだけ。公開版には出ない。
- ローカルproxy: 回答APIの1要求ごとに `path` `status` `durationMs` `delivered` `events`（種類別の件数）`error`（失敗コード）`answerChars` `audioFrames` `trace`（段階の並び）を1行のJSONとして `MENDAN_PREVIEW_LOG` へ追記し、同じ要約を標準出力にも出す。
- サーバー: 失敗時は診断コードを `console.info` へ出す。プレビュー版はCloudflareの実行ログ保存を有効にしていないため、クラウド側だけを後からたどることはできない。確認はローカルの記録を使う。

失敗のコードは原因ごとに分ける。`answer_timeout` は応答全体の時間切れ（既定25秒）、`answer_aborted` は利用者による停止、`stream_failure` は応答ストリームが例外で終わった場合で、`reason` が `iterator_threw`（想定外の例外）か `iterator_aborted`（中断）を示す。時間切れは「時間内に回答をまとめられませんでした。」と案内し、`JEV_UNAVAILABLE`（確認サービスへ接続できない）・`ANSWER_REJECTED`（内容を確認できない）と区別する。

## 採点設定の管理画面

本人が、回答の採否を画面から調整できる。設定はD1（`jev_settings_versions`、migration 0003）へ版つきで保存し、保存のたびに再デプロイを要さない。

| 操作できる内容 | 補足 |
| --- | --- |
| 項目別の閾値 | 0〜1。`score < threshold` を不合格とし、同点は合格。 |
| 各項目の扱い | `必須`（1つでも不合格なら不採用）/ `任意`（不合格件数に数える）/ `記録のみ`（採否に使わない）。 |
| 任意項目の不合格件数 | この件数以上で不採用。0は「任意だけでは不採用にしない」。 |
| 実行の上限 | 直列段階1〜3、段階内の判定1〜10、修復0〜1、回答全体とJEV1回の時間予算。範囲外は保存前に拒否する。 |
| 保存・復元 | 現在の設定の確認、保存、直前の版へ戻す、初期値へ戻す。 |
| 生成前の選別（JEV①） | 行うかどうか、段階内の判定数、8項目の閾値（答えに使えるかの軸は「以上で満たす」、注意の軸は「以上で注意」）。 |
| 選別の確信度 | confidenceの閾値と、低確信のときの行き先（そのまま使う／2段目／控えめ／保留）。 |

- 直列の段階数は実際の実行を決める。1=点検のみ、2=選別＋点検、3=選別＋点検＋修復後の点検。段階数が2なら修復は行わない。低確信の2段目も1段階として数える。
- 段階内の判定数はHTTPの回数ではない。1回のリクエストへまとめる独立判定の数で、上限を超える軸は聞かず、採否にも使わない（点検で聞かなかった軸は`unevaluated`として扱う）。
- 段階ごとの所要時間を記録し、管理画面にp50/p95と修復率（修復の生成÷回答の生成）を表示する。日本からの実測であり、公式の速さの保証ではない。

初期値は現行の挙動（全軸必須・全軸合格が必要、閾値は既存の環境設定）をそのまま表す。実装者が必要な軸を選び直したり、閾値を一律に下げたりしない。採点そのものは現行の6軸のままで、採否だけを設定で決める。スコアは未校正の判定値で、正答率ではない。

設定は質問の開始時点で確定し、回答の途中に保存されてもその質問の点検・修復へ混ぜない。文字画面と音声画面は同じ保存設定を使う。各回答の実行記録には、`answer_context` として `settingsVersion` と `settingsSource`（`stored`/`default`/`invalid`）と `scores` を残す。保存値が壊れていた場合は既定へ戻し、`jev_settings_fallback` を記録する。

管理画面は `/admin` にある。画面は鍵なしで開けるが、設定の読み書きはサーバー側で拒否する。管理鍵はWorkers Secretの `ADMIN_TOKEN` で、`x-mendan-admin` ヘッダーを定時間比較する。試用版を見るための `PREVIEW_ACCESS_TOKEN` とは別の鍵にする。鍵が未設定なら常に拒否する。秘密の値は画面・ログ・Issueへ出さない。

画面には、直近に実行した採点（回答の点検と生成前の選別で別々、本文なし）を最大10件残し、いま編集中の設定を当てた採否例を表示する。採点を作り直すための回答やJEVの再実行はしない。

公開・承認・所有者・現行版の確認、認証、利用制限、Secret保護は、この採点設定では解除できない。JEVの通信障害・不正な応答・必須値の欠落は、閾値を下げても合格にしない。

切り戻しは `ANSWER_PIPELINE=legacy` を指定した新しいプレビュー版を作り、ローカルproxyの接続先を切り替える。本人向け保護は維持する。プレビューの停止だけならproxyを終了する。公開サイトの稼働版は今回変更していない。

## 確認結果と制約

- 型チェック、ユニット369件、本番用Workerビルドが通過した。JEVの通信を模擬した本体APIで、Fact維持、生成・JEV上限、撤回、中止、エラー、復帰、音声への同一本文の受け渡し、既存のOrigin・利用制限を確認した。失敗時は、時間切れと中止を区別したコード、止まった段階の記録、失敗した応答へ段階を付けて返すことを確認した。加えて、Choice/Score/Noulの用途分離、confidenceと低確信の行き先、段階数・判定数・修復回数が実際の実行を決めること、候補集合の外の主根拠を採用しないこと、段階ごとの時間と採点の控えを確認した。
- 実APIで、構造化stateとChoice/Score/Noulの送受信を架空の資料で確認した（東京から: 選別10判定で719ms、入力1,481・出力282トークン、点検で318ms、入力1,289・出力121トークン）。本人の資料は送っていない。
- 試用版の実行記録から、段階ごとの実測は 生成前の選別 p50 442ms（379〜535ms、6回）、回答の点検 p50 441ms（170〜654ms、8回）だった。回答の生成は p50 6.7秒で 2.4〜14.5秒、予算25秒を超えて中断した回もある。待ち時間の大半とばらつきは生成側にある。時間予算の既定は60秒（上限）へ広げ、管理画面から3〜60秒で調整できる。長さ超過の差し戻しは、実際の字数と上限を修復指示へ入れる。
- 生成前の選別の追加軸（因果の未確認）を生成の指示へ常に反映するようにしたため、資料に因果が無い質問では最初の候補が因果軸で差し戻されにくくなる見込み。効果は本人の資料での試用で確認する。
- 既存画面から本体のAPIハンドラーへ接続し、架空データと外部応答の模擬で、文字・音声のJEV障害後の復帰、停止後の再質問、読み上げ後の次の質問を確認した。別途、音声画面のJEV障害のブラウザ回帰1件が通過した。
- 自動の実API確認は8問、各1回。通常6問、故意に因果を誤らせた候補の修復1問、合成音声の挨拶1問。生成8回・JEV9回・STT1回。旧D評価の使用数とは分けている。
- 通常6問は5問が回答、由来の1問は修復後も「不要な棄権」軸で却下された。回答が出た5問の画面表示は中央値5.36秒、範囲1.53〜9.93秒。拒否された1問は23.55秒。目標の中央値5秒以内は未達。初回・修復候補本文を保存しておらず、この1問が誤拒否かどうかは未確定。
- 因果を誤らせた1問では、JEVの根拠支持0.06・因果の非創作0.08で初回候補を却下し、修復後の部分回答だけを表示した。通常生成の正答率には数えない。
- JEVは9回の中央値0.49秒。検索は架空のメモリDB・固定ベクトルを使っており、本番検索の速度・精度を示す値ではない。本人資料への自動質問はしていない。
- 合成の「こんにちは」のSTTは3.37秒。既存音声画面で文字応答と入力復帰を確認した。手入力の初期設定が読み上げオフだったため、この実API確認ではTTSは未実行。実TTSの時間・実マイクの認識精度・本人資料での品質は本人試用で確認する。模擬TTSの確認結果と区別する。

JEVの速度だけで会話全体が速くなるとは限らず、生成と修復に待ち時間が残る。少数の架空例で、本人資料での誤回答や誤拒否がなくなることを保証しない。
