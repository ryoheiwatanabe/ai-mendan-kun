# 根拠に基づく会話の受入評価

`tests/fixtures/grounded-acceptance.json` の架空人物資料7件と、20ケース×3通りの質問を使う。苦手・課題への意味対応、担当範囲と否定、年別数値、部分回答、限定的な見立て、名称の追質問、会話履歴の誤情報、50字指定、詳細要求の否定、挨拶を確認する。

`scripts/grounded-eval.ts` は各資料を別々に承認してメモリDBへ投入し、実際の回答engineを呼ぶ。実在人物の資料や公開DBを読み書きしない。検索候補には固定ベクトルを使用するため、実際の検索精度を測る評価ではない。本文の意味、回答の直接性、不要な繰り返しは別途レビューする。

## 実行

```sh
node --experimental-strip-types scripts/grounded-eval.ts \
  --adapter .local/grounded-evaluation/gateway-adapter.ts \
  --allow-api-cost --cases case-07,case-10,case-18 --variants 1 --label candidate-smoke
```

adapterは `createEvaluationProviders()` から `provider` と `model` を返すローカルモジュール。必要に応じて旧版の `engine`、`voiceEngine`、`speech` も注入できる。上記adapterは検証時だけ用意するGit対象外のファイルで、配布物には含めない。harnessはAPIキーの取得・保存を行わない。CLIの費用確認フラグがない場合はadapterを読み込む前に停止する。

case指定なしでは先頭3ケース、variantsの初期値は1。variantsは1〜3を指定できる。全60問は全case IDとvariants 3を明示し、小規模評価の費用・失敗を確認してから実行する。通信等のエラー時は後続を停止する。診断目的で関数へ `continueOnFailure: true` を渡した場合だけ、根拠・長さ・校閲の品質拒否後も別の質問へ進める。通信や生成エラーでは、この指定があっても停止する。harness独自の回答再生成は行わず、engineが行う再生成も含め、生成最大2回・校閲最大2回を計測する。

## 保存と判定

出力は `.local/grounded-evaluation/` 配下のUUID付きNDJSONとsummary JSON。回答本文は架空資料に対するものだけを保存する。各回答を保存後に同期し、既存ファイルは上書きしない。

機械判定はdone受信、期待する回答可否、最終本文のUnicodeコードポイント数、呼出回数。`requiredClaims` と `forbiddenClaims` は意味を読むレビュー用で、文字列一致だけで正誤を決めない。`semanticReview: pending` はレビュー未実施を表す。機械判定の合格率を回答精度と呼ばない。

生成・校閲のAPI呼出数、返された入出力トークン、本文表示までの時間、処理完了までの時間を保存する。TTSを注入した場合のみ、TTS呼出数と音声チャンク数を分け、最初の回答音声が返る時間も計測する。初回本文・初回音声・処理完了のp50/p95と件数を出す。再生完了はブラウザの確認が必要で、ここではnull。usage欠落はunknown、単価が未指定なら費用はnullとする。費用はテキスト生成・校閲分の推定であり、TTS料金は含めない。

旧版と新版には、同じfixture、質問、言い換え番号、モデルを使う。旧版は旧Providerの生成プロンプトも含めて読み込む。ローカルgatewayやネットワークの時間を含む結果なので、公開環境の待ち時間を保証する数値として使わない。少数例のp95は参考値であり、サンプル数を必ず併記する。

## 2026年9月15日 引き継ぎ後の再評価

前節の「残る観点」を確認するため、同じ架空資料7件と20ケースの最初の言い回しを、Gemini 3.8 Flashで改めて実行した。変更前の20件は機械判定をすべて通過したが、意味を読むと3点が残っていた。

| 観点 | 変更前の例 | 変更後の例 |
| --- | --- | --- |
| 面談で硬い言い方 | 「継続についての改善策や克服の記録はありません。」 | 「継続への改善策についてはまだ確認できていないため、面談で本人に確認してください。」 |
| 質問に不要な未記録の補足 | 担当範囲への回答へ「正式なPdMの肩書での経験はありません」を付け足す | 質問が求めた担当範囲だけを答える |
| 短い回答での担当範囲 | 50字指定で「要件整理を担当しています。」(20字) | 「要件整理を担当し、実装は外部エンジニアが担当しました。」(27字) |

評価の途中で2件の不具合も見つけた。

- 生成後の機械検証が、「〜はまだ決まっていない」「面談で本人に確認してください」という語形を不足説明として認めず、正しい候補を却下していた。根拠の本文に「開始可能日はまだ決まっていない。」と書かれていても、候補がその語形を使うと不合格になり、再生成へ進んでいた。
- 修復生成が棄権(segmentsが空)を返したとき、利用者には「処理に失敗しました。」が出ていた。初回生成の棄権は定型の不明回答へ戻す設計なのに、修復だけ処理失敗として扱われていた。

対応は次のとおり。変更後は、回答生成のプロンプトが`lib/ai/prompt.ts`のSHA-256先頭12桁`6c6e4b816d07`、候補の機械検証が`lib/answer/guard.ts`の`4184191b92e2`、回答engineが`lib/answer/engine.ts`の`f5c20ae6ba93`。

- 回答生成のプロンプト: 質問で尋ねていない事項へ「記録がない」「不明」「未確認」を付け足さない、不足説明は質問が求めた事項に限る、仮定の相談では未経験を理由にpartialへ下げない、不足説明は「〜はまだ確認できていない」「〜はまだ決まっていない」のような面談に合う言い方へそろえる、役割や担当範囲は短い指定でも担当しない範囲まで残す、を明示した。
- 候補の機械検証: 不足説明として認める語形へ「未定」「まだ決まっていない」「本人が判断・決定する」を追加し、確認の依頼（「面談で本人に確認してください」）はその文が依頼だけで事実の断定を含まない場合に認める。数値や役職名を含む文は従来どおり拒否する。
- 回答engine: 修復生成の棄権も、初回と同じ定型の不明回答と`model_abstained`へ戻した。
- テスト: 追加した語形を受け入れて数値入りの無根拠claimを拒否すること、修復棄権で処理失敗にしないことを追加した。
